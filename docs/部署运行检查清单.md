# 部署运行检查清单

适用部署方式：项目根目录 `docker compose up -d`（SQL Server + Redis + 后端 + 前端）。
访问约定：前端 `http://localhost:3665`、后端 `http://localhost:8665/jeecg-boot`、SQL Server `localhost:1433`，默认账号 `admin/123456`。

> 建议逐项勾选，每一步确认“预期结果”后再进入下一步；异常时参照文末两章排查。

---

## 1. 容器与启动顺序检查

```bash
docker compose ps
docker compose logs -f db-init   # 初始化日志，结束后该容器应 Exited(0)
docker compose logs -f backend   # 看到 “Started ... Application” 即启动完成
```

- [ ] 预期结果：`jeecg-sqlserver`、`jeecg-redis`、`jeecg-backend`、`jeecg-frontend` 状态为 `Up`；`jeecg-sqlserver-init` 状态为 `Exited (0)`（一次性初始化容器，退出码必须为 0）。
- [ ] 预期结果：后端日志末尾出现 `Started JeecgSystemApplication`（或同类 “Started ... in x seconds”），无 `Connection refused`、`Login failed`、`Communications link failure` 等堆栈。

## 2. 后端启动检查（服务可达性）

```bash
# 直连后端健康/验证码接口（GET 不会真正登录，只验证服务存活）
curl -i http://localhost:8665/jeecg-boot/sys/randomImage/1700000000000
```

- [ ] 预期结果：返回 `HTTP/1.1 200`，响应体为图片二进制（验证码图），说明 Spring Boot、context-path（`/jeecg-boot`）均正常。
- [ ] 预期结果：浏览器直接访问 `http://localhost:8665/jeecg-boot/` 根路径不报 502/连接拒绝（返回 401/404 均属正常，服务已起）。

## 3. 前端访问检查

- 浏览器打开 `http://localhost:3665`。
- [ ] 预期结果：显示 JeecgBoot 登录页，静态资源（JS/CSS/图片）无 404、无白屏。
- [ ] 预期结果：前端通过 Nginx 反代访问后端：`http://localhost:3665/jeecgboot/...` 请求返回正常（开发者工具 Network 中无 `502 Bad Gateway`、无 `ERR_CONNECTION_REFUSED`；Nginx 配置为 `/jeecgboot/ → http://backend:8080/jeecg-boot/`）。

## 4. 登录与数据库连接联查

在登录页输入 `admin / 123456`（按页面要求输入验证码）。

- [ ] 预期结果：登录成功，进入系统首页，右上角显示 admin 用户，左侧出现系统菜单。
- [ ] 预期结果：能登录即说明 **后端 → SQL Server（库名 `temp1218`）** 与 **后端 → Redis（6379，Token/验证码缓存）** 两条链路均通；后端日志无 SQL 异常。
- [ ] 补充验证（容器内直连数据库）：
  ```bash
  docker exec -it jeecg-sqlserver /opt/mssql-tools18/bin/sqlcmd -S localhost,1433 -U sa -P 'Supcon1304' -C -d temp1218 -Q "SELECT COUNT(*) FROM sys_user;"
  ```
  预期结果：成功返回用户表行数（至少包含 admin 种子账号），无 `Login failed for user 'sa'`、无 `Cannot open database "temp1218"`。

## 5. 设备档案菜单检查

设备档案为 JeecgBoot 在线开发/系统菜单中配置的业务菜单（菜单数据存于 `sys_permission`）。

- [ ] 预期结果：admin 登录后，左侧导航可见“设备档案”菜单项，点击后页面正常打开，列表区域出现查询表单、操作按钮（新增/批量删除/导出等）与数据表格（首装可为空表但列头完整）。
- [ ] 预期结果：Network 中列表查询请求（形如 `/jeecgboot/<设备模块>/deviceProfile/list` 或实际配置的 `list` 接口）返回 `200`，响应 JSON 中 `success: true`、`records`/`total` 结构完整。
- [ ] 若菜单不显示：预期排查结果为“角色未授权菜单”——以 admin 在【系统管理 → 角色权限】中给对应角色勾选“设备档案”及按钮权限后重新登录可见。

## 6. 设备档案增删改查（CRUD）检查

| 操作 | 步骤 | 预期结果 |
|---|---|---|
| **新增（C）** | 点【新增】填写设备编号、设备名称等必填项后保存 | 提示“添加成功/操作成功”；列表自动刷新出现新记录；后端日志 INSERT 无报错；数据库中可查到该记录 |
| **查询（R）** | 在查询区输入设备编号/名称点【查询】，并翻页 | 列表按条件过滤正确，分页总数与实际一致；重置按钮可恢复全量 |
| **修改（U）** | 选中记录点【编辑】，修改字段后保存 | 提示“操作成功”；列表即时显示新值；再次打开编辑表单为修改后的内容（DB 已 UPDATE） |
| **删除（D）** | 单条【删除】并确认；再测试【批量删除】 | 提示“删除成功”，记录从列表消失（JeecgBoot 默认逻辑删除 `del_flag`，列表不再出现即符合预期）；批量删除条数与勾选数一致 |

- [ ] 预期结果：四项操作的前端提示均为成功，刷新页面后数据状态保持一致，无脏数据、无 500 错误。

## 7. 权限验证检查

1. 以 admin 在【系统管理 → 用户管理】建一个测试用户（或使用既有低权限账号），其角色**不授予**“设备档案”菜单。
2. 退出 admin，用该用户登录。
- [ ] 预期结果（菜单级）：左侧导航**看不到**“设备档案”入口，直接手敲该页面 URL 也无法进入数据页。
3. 用该用户的 Token 直接调用设备档案接口（复制浏览器请求为 curl，或在未授权会话中 fetch）。
- [ ] 预期结果（接口级）：后端返回 `403`/`500`（JeecgBoot 权限注解拦截，提示“无权限访问/该操作需要授权”），**不返回**业务数据；新增、删除、导出等按钮权限同样被拦截。
4. 切回 admin，给该角色勾选“设备档案”的“查看”但不勾“新增/删除”，重新登录。
- [ ] 预期结果（按钮级）：可进入列表查看数据，但页面不显示【新增】【删除】按钮；强行调用写接口仍被后端拒绝（前端隐藏只是第一层，后端鉴权必须同时生效）。
- [ ] 预期结果（登录侧）：错误密码登录提示“用户名或密码错误”；连续异常不会返回 Token。

## 8. 端口冲突排查

涉及端口：`3665`（前端）、`8665`（后端）、`1433`（SQL Server）。

现象：`docker compose up` 时报
`Bind for 0.0.0.0:8665 failed: port is already allocated`，
或前端页 502、本机其他程序占用导致容器反复重启。

1. 查占用进程：
   ```bash
   # Linux
   sudo lsof -i :8665 -i :3665 -i :1433
   sudo ss -lntp | grep -E '3665|8665|1433'
   # macOS
   lsof -nP -iTCP:8665 -sTCP:LISTEN
   # Windows (PowerShell)
   netstat -ano | findstr "8665 3665 1433"
   ```
2. 预期处理（任选其一）：
   - 停止占用端口的旧容器/旧服务（常见是上一次未关的 `jeecg-*` 容器：`docker compose down` 或 `docker rm -f` 旧容器）；
   - 或修改 `docker-compose.yml` 中宿主机映射端口（例如把 `"8665:8080"` 改为 `"8666:8080"`，前端 `"3665:80"` 改为 `"3666:80"`），并同步用新端口访问；
   - `1433` 常被本机已装的 SQL Server 服务占用：停止本地 SQL Server 服务，或把映射改为 `"1434:1433"`（注意此时后端容器内部仍走 `db:1433`，不受影响；仅影响宿主机直连工具的端口）。
3. 处理后预期：`docker compose ps` 全部 `Up`，三个端口 `curl`/浏览器访问恢复正常。

## 9. 数据库登录失败排查

现象：后端日志出现
`Login failed for user 'sa'. ClientConnectionId:...`、
`Cannot open database "temp1218" requested by the login`、
`The TCP/IP connection to host db, port 1433 has failed`，
或 sqlcmd 直连报 18456/18470 错误。

按下列顺序排查：

1. **sa 密码不一致（最常见）**。若启动时用 `MSSQL_SA_PASSWORD=xxx` 自定义过密码，SQL Server 数据卷里固化的是**第一次初始化**的密码；之后改密码但未清卷会导致后端用新密码、库仍是旧密码。
   - 处理：`docker compose down -v`（⚠️ 删除持久化数据）后重新 `up -d`，保证 db / db-init / backend 三处密码同源（均取 `${MSSQL_SA_PASSWORD:-Supcon1304}`）。
2. **密码复杂度不达标**：SQL Server sa 密码要求至少 8 位且含大小写字母、数字、符号。自定义密码过简单会导致 db 容器虽在运行但 sa 不可用（日志可见 `ERROR: Unable to set system administrator password`）。需改用强密码并重新初始化卷。
3. **目标库不存在 / 初始化失败**：确认 `jeecg-sqlserver-init` 退出码为 0：
   ```bash
   docker compose ps -a | grep init
   docker compose logs db-init | tail -50
   ```
   若为非 0 退出，`temp1218` 未建表，后端即报 “Cannot open database”。根据 init 日志修正后 `docker compose up -d --force-recreate db-init backend`。
4. **连接参数问题（宿主机直连工具）**：主机填 `localhost,1433`（注意是逗号），认证选 SQL Server 认证，用户名 `sa`，数据库显式选 `temp1218`；容器内 `sqlcmd` 需加 `-C`（信任自签证书）并使用工具路径 `/opt/mssql-tools18/bin/sqlcmd`。
5. **db 尚未就绪后端就连了**：正常 Compose 已用 `depends_on: db-init` 串行化；若后端偶发首启失败，`docker compose restart backend` 重试即可，预期第二次启动成功。
6. **容器网络不通**：后端必须用服务名 `db:1433`（见 `SPRING_DATASOURCE_..._URL=jdbc:sqlserver://db:1433...`），不要在容器内写 `localhost:1433`——那指向后端容器自身。
7. **Redis 连带问题**：登录失败但报的是验证码/Token 异常时，检查 `jeecg-redis` 是否 `Up`，后端环境变量 `SPRING_DATA_REDIS_HOST=redis`、端口 `6379`。

排查后预期：第 4 步中的 sqlcmd 查询成功返回用户数，admin 可正常登录，后端日志不再出现连接/登录异常。
